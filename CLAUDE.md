## What this is

Gislefoss is a **.NET 10 / .NET Aspire 13.1** application. The intended product (see `docs/idea.md`) is a **"Meteorologist" AI agent** that answers only weather-related questions and declines everything else. Planned stack: Microsoft Agent Framework, Azure AI Foundry, an OpenAI model, a persona loaded from an external Markdown file, with prompt-injection protection / prompt shields / content filters, deployed via Bicep.

**Current state: server-side persistent-agent migration implemented; backend deployed live (2026-06-13), agent memory enabled live (2026-06-22, agent now version 2), a custom PII RAI blocklist deployed + proven live (2026-06-22), and an Application Insights account connection for server-side agent tracing deployed + control-plane-verified live (2026-06-23); the Web-app container deploy is the only remaining step.** The agent runtime is wired: `src/Agent/Foundry/MeteorologistAgentFactory.cs` obtains the `AIAgent` server-side, by name (`AsAIAgent` + `AgentReference`; an asst_ id is rejected by the SDK name regex), `src/Agent/Foundry/FoundryAgentRunner.cs` adapts it to the `IFoundryAgentRunner` port, DI is wired in `src/Agent/ServiceCollectionExtensions.cs`, and `src/Web/Program.cs` no longer reads the persona at boot, fetching the agent lazily on first use; tests are green. The Blazor home page (`src/Web/Components/Pages/Home.razor`) is still the default "Hello, world!" stub, but a functional weather chat UI exists at `src/Web/Components/Pages/Chat.razor`. What exists: a complete persona at `personas/gislefoss.md` (a top-level repo asset, sibling to `src/` and `infra/`, embedded into the agent at deploy time via Bicep `loadTextContent` in `infra/main.bicep`; no longer copied into the Web output), plus an `Agent` class library and an `Agent.Tests` xUnit project (Phases 1–5) holding value types, `AgentOptions`, run-outcome inspection, a conversation facade, the factory, the runner adapter, and DI — all built and green. The Bicep infrastructure under `infra/` was **deployed live on 2026-06-13** into resource group `rg-gislefoss-sdc` (Sweden Central) as the `gislefoss-backend` deployment (`deployApp=false`): the Foundry account/project, the gpt-4o (GlobalStandard) model deployment with a **block Guardrail** attached, account + project **capability hosts** (Agent Service enabled, `2025-04-01-preview`), Log Analytics + App Insights, the provisioning UAMI (`identity.bicep`), the provisioner RBAC assignment (`roles.bicep` — UAMI → Azure AI Developer), and the agent-upsert deployment-script (`agent.bicep` + `infra/scripts/upsert-agent.py`) that created the server-side agent (originally version 1). A later deploy (`gislefoss-memory`, **2026-06-22**, `deployApp=false deployMemory=true`) turned memory ON and bumped the agent to **version 2**: it added the embedding deployment (`model-gislefoss-embedding-sdc` — text-embedding-3-small v1, **GlobalStandard** SKU; `Standard` is not offered in Sweden Central), the memory store **`mem-gislefoss-sdc`** (`memory.bicep` + `infra/scripts/provision-memory.py`, via `AIProjectClient.memory_stores.create` — no `.beta`, no `attach_memory`), a **Foundry User** (`53ca6127-...`) role assignment on the **project** for the project's own system-assigned identity (`roles-project.bicep` — this is what clears the portal "Setup incomplete: assign the Foundry project's managed identity the Foundry User role for this project" banner), and a **`MemorySearchTool`** (`scope="{{$userId}}"`) on the agent definition binding it to the store. The deployed agent is therefore now **stateful** (long-term memory), with two caveats: (a) **TTL is unsupported** on the pinned `azure-ai-projects==2.0.0b2` — `MemoryStoreDefaultOptions` has no `default_ttl_seconds`, so the store has **no expiry** (`provision-memory.py` warns; honoring `memoryTtlSeconds` needs an SDK bump), and (b) per-user memory **isolation is dormant** until the Web app ships and sends an `x-memory-user-id` header (an app-side change in `FoundryAgentRunner`). Note the binding tool in 2.0.0b2 is `MemorySearchTool`, NOT the `MemorySearchPreviewTool` shown in the public `>=2.0.0` docs. Still authored but **gated off** (`deployApp=false`): the Web app + its inference role (`app.bicep` + `roles-app.bicep`, behind `deployApp`). The project **has migrated to a server-side persistent Foundry agent**: the persona stays in git (`personas/gislefoss.md`) and is pushed to the agent on each deploy by `infra/modules/agent.bicep` — a deployment-script that, via `azure-ai-projects` 2.0.0b2 (`AIProjectClient.agents.create_version`/`.create` with a `PromptAgentDefinition`), upserts the agent **by name** and publishes a new version carrying the current persona (the persona is delivered as a file, not an env var, to dodge the ACI env-var size limit). The app retrieves it by name (config key `Settings:Agent:AgentName`; code default `Gislefoss`, but the live agent is `agent-gislefoss-sdc` — the CAF name `main.bicep` upserts under and `app.bicep` injects); name-keyed retrieval gets the latest version. The previously-flagged deploy-verify items are now **resolved live**: the capability-host preview shape worked first try, the `create_version`/`create` upsert path created/updated the agent, and the Guardrail's content filters (all 10 blocking and enabled — including `Jailbreak` and `Indirect Attack`) read back as expected. A **custom PII RAI blocklist** was then deployed + proven live (2026-06-22, ARM deployment `gislefoss-blocklist`, `deployBlocklist=true`): `blocklist-gislefoss-sdc` with 5 regex items (`email`, `us-ssn`, `credit-card`, `us-phone`, `ipv4`; `isRegex=true`, unanchored) attached to the Guardrail's `customBlocklists` on **both** Prompt and Completion (`blocking:true`). It is authored **in-file** in `infra/modules/foundry.bicep` (deliberately not a separate module — a foundry→blocklist→foundry module cycle otherwise) and gated by `deployBlocklist` (defaults **true** in `main.bicep`, name `blocklist-${prefix}-${region}`). It augments the Guardrail on the chat deployment (`model-gislefoss-chat-sdc`), so it fires on **every call** independent of the agent/app — verified by a direct deployment call: a prompt containing an email returns **HTTP 400 `content_filter`** with `content_filter_result.custom_blocklists = [{filtered:true, id:"blocklist-gislefoss-sdc"}]` while every built-in filter stays `filtered:false`, and a clean weather prompt returns **200**. Two deploy gotchas are documented in `foundry.bicep` comments: (1) the CognitiveServices RP **preflight** validates the policy's `customBlocklists` reference against EXISTING state up front (so `dependsOn` does NOT help — the empty list must be pre-created out-of-band once, `az rest --method put .../raiBlocklists/<name>?api-version=2024-10-01`, before the first deploy); (2) the item loop needs **`@batchSize(1)`** to serialize writes — parallel item writes each carry the parent blocklist's ETag as `If-Match` and race, failing `IfMatchPreconditionFailed` (and then skipping the Guardrail attachment). The agent stayed **version 2** (the blocklist doesn't touch the agent definition; the re-upsert was a no-op). An **Application Insights account connection** was then deployed live (2026-06-23, ARM deployment `gislefoss-appinsights`, `connectAppInsights=true`): a new `infra/modules/observability-connection.bicep` creates an **account-level** connection `aif-gislefoss-sdc-appinsights` (`Microsoft.CognitiveServices/accounts/connections@2025-04-01-preview`, `category:'AppInsights'`, `target`=the `appi-gislefoss-sdc` resource ID, `authType:'ApiKey'` where the credential "key" is the App Insights **connection string** — deliberately ApiKey, since AAD/ManagedIdentity would require a Monitoring Metrics Publisher RBAC grant; `metadata:{ApiType:'Azure',ResourceId:<id>}`, `isSharedToAll:true`), wired in `main.bicep` behind `connectAppInsights` (defaults **true**, name `${foundryName}-appinsights`). This is the IaC equivalent of the Foundry portal's "Create or connect an App Insights resource" / project Monitoring tab, and it makes the **Foundry Agent Service emit server-side agent traces** (agent runs, model/tool calls, token usage) to App Insights — distinct from the Web app's client-side OTel export (`app.bicep`), so it works with `deployApp=false`. Account `disableLocalAuth` is orthogonal (it governs the account's own inference keys, not this connection's stored credential). **Verified at the control plane**: GET returns the connection with the properties above (credentials masked to null on read — normal), and the **project** connections list shows it as `isDefault:true, isSharedToAll:true` (= what the Monitoring tab reads). **Not yet end-to-end-confirmed**: an actual agent-run trace landing in App Insights (needs an agent run + a few minutes of ingestion). Account-level is the documented standard (foundry-samples `01-connections/connection-application-insights.bicep`); the fallback if the tab somehow stays empty is a project-level connection (`accounts/projects/connections`, parent=project). The agent stayed **version 2** (the connection doesn't touch the agent definition). **Remaining:** the Web app itself (`deployApp=true`) is not yet deployed — it needs a container registry plus a built/pushed image, which are not yet wired; and to activate per-user memory isolation the app must send an `x-memory-user-id` header per request (the agent's `MemorySearchTool` scope `{{$userId}}` is otherwise dormant). **`deployMemory` now defaults `true` in `main.bicep`** (matching the live posture), so the app deploy keeps memory bound automatically — do **not** pass `deployMemory=false`, or the always-on agent re-upserts with no memory tool and silently reverts to stateless. See the migration plan at `docs/superpowers/plans/2026-06-07-meteorologist-agent-foundry-server-side-migration.md`. `Azure.AI.OpenAI` 2.1.0 is referenced and `Settings` already has an `AzureOpenAI` config block. Treat `docs/idea.md` as the requirements spec, not a description of existing code.

## Commands

All projects target `net10.0` (SDK 10.0.300+). The solution file is `src/Gislefoss.slnx` (XML-format solution).

```powershell
dotnet restore src/Gislefoss.slnx
dotnet build src/Gislefoss.slnx

# Local development WITH the Aspire dashboard (orchestrates the Web app):
dotnet run --project src/AppHost          # dashboard on http://localhost:15175

# Run the Web app directly (no orchestration):
dotnet run --project src/Web              # app on http://localhost:8087
```

Tests live in `src/Agent.Tests` (xUnit), part of `src/Gislefoss.slnx`:

```powershell
dotnet test src/Gislefoss.slnx
```

## Architecture

Four projects (`src/Gislefoss.slnx`):

- **AppHost** — the .NET Aspire orchestrator (`Aspire.AppHost.Sdk/13.1.0`). `AppHost.cs` registers the Web project (`builder.AddProject<Projects.Web>("web")`). This is the entry point for local development with the dashboard. Holds the `UserSecretsId`, so user secrets attach here.
- **Web** — Blazor Server app: Razor Components with **Interactive Server** render mode, **MudBlazor** as the component library. Vendored Bootstrap/jQuery exist under `wwwroot/lib` but MudBlazor is what's actually used.
- **Library** — shared helpers: configuration-key enumeration/logging (`AllConfigurationKeys`, `LogStrings`, `OutputEnvironmentVariables`), an `AddOpenTelemetry` that wires **Azure Monitor**, and a `MapDefaultEndpoints(applicationStartTime)` that adds `/livez`, `/uptime`, and `/error`.
- **ServiceDefaults** — the standard Aspire defaults (OpenTelemetry, health checks, service discovery, HTTP resilience) exposed via `AddServiceDefaults()`.

### Important: Web bypasses the standard Aspire wiring

`src/Web/Program.cs` is a **custom** host setup, not the default minimal template, and this is the easiest thing to get wrong:

- It does **not** call `AddServiceDefaults()` and does **not** use ServiceDefaults' `MapDefaultEndpoints`. Instead it uses **Library's** `AddOpenTelemetry` and **Library's** `MapDefaultEndpoints`. So service discovery / standard resilience are not active, and the `/health` + `/alive` endpoints from ServiceDefaults are not mapped. If you need them, wire them explicitly.
- Configuration is built **manually**: `appsettings.json` + `appsettings.{DOTNET_ENVIRONMENT}.json` (optional) + environment variables. The `Settings` section is bound to the `Settings` POCO (`src/Web/Settings.cs`) and registered as a singleton; **startup throws if the `Settings` section is missing**.
- Logging is **Serilog**: a bootstrap console logger first, then the real logger read from the `Serilog` config section. At startup it logs every environment variable (Debug level) and every resolved configuration key — be mindful that secrets in config will surface in logs.

### Configuration & secrets

- Azure OpenAI settings live under `Settings:AzureOpenAI` → `Endpoint`, `ApiKey`, `DeploymentNameChat`.
- Local secrets go in **user secrets** (AppHost) or `appsettings.Development*.json`, which is **gitignored** (`appsettings.Development*.json`). Do not commit keys.
- OpenTelemetry → Azure Monitor activates only when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set (Aspire injects it locally).

### Endpoints & ports

- Web listens on **port 8087** (set in both `appsettings.json` Kestrel config and the Web `http` launch profile).
- Custom endpoints: `/livez` (liveness), `/uptime` (uptime JSON), `/info` (lists endpoints), `/error`; 404s re-execute to `/not-found`.
- Aspire dashboard runs on **localhost:15175** when launched via AppHost.

### Containerization

`src/Web/Dockerfile` builds the Web project on a chiseled .NET 10 ASP.NET base image, exposes 8087, entry point `dotnet Web.dll`. `DockerDefaultTargetOS` is Linux.
